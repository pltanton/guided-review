# Guided review — дизайн

Дата: 2026-09-25
Статус: на ревью

## Цель

Упростить и ускорить ревью MR, не теряя качества и надёжности. Агент понимает
задачу и реализацию, составляет план обхода и ведёт человека по нему
маленькими шагами с короткими пояснениями. Человек смотрит код во вьювере с
LSP-навигацией и отвечает агенту в чате.

Анти-цель: «LGTM, поехали». Защита встроена в инструмент, а не в дисциплину.

## Контекст и ограничения

- Команда: Go, Python, Kotlin. Редакторы — neovim, helix. Агент (Claude Code
  или Codex) работает в терминале в tmux.
- Форж: только GitLab. GitHub — позже, за тем же интерфейсом.
- Решение должно быть общим: раздать команде, в перспективе выложить публично.
- Вьювер и CLI — KISS/suckless, код по правилам `go-style:idiomatic-go`.

## Архитектура

```
┌─ tmux ─────────────────────────┬────────────────────────────┐
│ claude / codex                 │ gr view                    │
│  скил guided-review            │  текущий шаг + LSP-попапы  │
│   │                            │   ▲                        │
│   └── gr <cmd> ──► state ◄─────┼───┘ (fsnotify)             │
└────────────────────────────────┴────────────────────────────┘
                  .git/guided-review/<id>/state.yaml
```

Три части и один контракт:

1. **Скил `guided-review`** — протокол ревью в markdown. Один текст для Claude
   Code (плагин) и Codex (`AGENTS.md`). Агент принимает решения: понимание
   задачи, план, пояснения, классификация замечаний.
2. **`gr`** — один Go-бинарь. Всё детерминированное: дифф, детект генеренки,
   валидация плана, переходы состояний, вьювер, публикация.
3. **Состояние** `.git/guided-review/<id>/state.yaml` — единственный контракт
   между агентом и вьювером и вся память ревью. Агент перечитывает его на
   каждом шаге, поэтому перезапуск или сжатие контекста не теряют нить.
   Лежит в `.git`, чтобы не засорять рабочее дерево.

### Команды `gr`

| Команда                                   | Что делает                                                                                                    |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `gr init <mr-url\|branch\|range>`         | собирает дифф и метаданные, помечает generated, проверяет HEAD == sha MR, проверяет `glab`, создаёт состояние |
| `gr plan set`                             | принимает план (YAML на stdin), валидирует, сохраняет                                                         |
| `gr step show\|next\|done\|skip --reason` | переходы по плану                                                                                             |
| `gr comment add`                          | комментарий с якорем: файл, строки, sha, уровень, опционально suggestion                                      |
| `gr status`                               | прогресс, покрытие, результат гейта                                                                           |
| `gr view`                                 | TUI-вьювер текущего шага                                                                                      |
| `gr publish [--dry-run] [--approve]`      | публикация в GitLab                                                                                           |

## Процесс ревью

### 0. Intake

Агент читает MR через `glab` (описание, связанная задача, дискуссии, пайплайн)
и пишет 2–3 строки «задача → как решено», сверяя их со спекой или описанием
MR. Затем спрашивает: «верно понял?».

### 1. Классификация изменений

Две независимые оси.

**Уровень (tier):**

- `generated` — детерминированно в `gr`: маркер `Code generated … DO NOT EDIT`,
  `linguist-generated` в `.gitattributes`, известные паттерны (`*.pb.go`,
  `build/generated/**`, lock-файлы), плюс паттерны из `.review.yaml`.
- `boilerplate` — решает агент: DI-wiring, мапперы DTO, регистрация роутов,
  тривиальные конфиги.
- `core` — всё остальное.

`generated` и `boilerplate` не становятся шагами. В плане остаётся сводка одной
строкой (`generated: 14 файлов, +2.3k (proto → go)`), по запросу её можно
раскрыть. Источник генерации (proto, openapi) — это контракт, он всегда core.
Агент коротко проверяет, что генеренка соответствует источнику (перегенерирована,
не правлена руками); расхождение — находка, а не шаг.

**Хотспоты** — места, где цена ошибки высокая:

- security: authn/authz, валидация входа, секреты и PII в логах, инъекции;
- консистентность: границы транзакций, гонки и double-spend, идемпотентность,
  outbox и порядок событий;
- деньги: округление, BigDecimal против float, валюты;
- миграции: блокировки, бэкфилл, обратная совместимость.

`.review.yaml` в репозитории задаёт чувствительность домена
(`domain: finance`): при ней категория «деньги» обязательна, планка выше.
Хотспот нельзя скрыть как boilerplate и нельзя пометить `stale`, если человек
явно этого не решил. Агент не утверждает «тут баг», а задаёт конкретный
вопрос.

### 2. План

Шаг:

```yaml
- id: s3
  title: "POST /transfers — хендлер"
  kind: contract | model | entry | logic | persistence | migration | test | config
  tier: core
  hunks: [{ file: api/transfer.go, lines: 40-92 }]
  hotspots:
    [{ cat: consistency, q: "повтор с тем же idempotency key после таймаута?" }]
  depends_on: [s1]
  status: pending | done | skipped | stale
  note: "Валидирует, резервирует сумму, пишет в outbox"
```

`gr plan set` отклоняет план, если:

- какой-то core-hunk не покрыт ни одним шагом;
- в `depends_on` есть цикл или ссылка на несуществующий шаг;
- у хотспота нет вопроса.

Порядок обхода: снаружи внутрь, дальше DFS.

1. Контракты: API-спека, proto, схема миграции, публичные интерфейсы.
2. Точки входа (хендлер, консьюмер, джоба), отсортированные по плотности
   хотспотов. От каждой — DFS по цепочке вызовов, только по изменённому коду.
   - Доменная модель — при первой встрече. Если MR про неё — отдельным шагом
     сразу после контрактов.
   - Тесты — сразу после юнита, который покрывают.
3. Остаток, не достижимый из точек входа: конфиги, утилиты, инфра —
   сгруппированными шагами.
4. Сводка boilerplate и generated.

Размер шага — примерно экран (40–80 строк диффа), одна мысль. Большую функцию
режем по hunk'ам, мелкие связанные hunk'и склеиваем.

### 3. Цикл шага

Агент пишет в чат по шаблону, не больше 5 строк:

```
s3/12 · POST /transfers — хендлер
Что: валидирует, резервирует сумму, пишет событие в outbox.
Спека: ⚠ требует 409 на дубль, тут 200
❓ Повтор с тем же idempotency key после таймаута — второе списание?
```

Строка «Спека» — только при расхождении, «❓» — только при хотспоте или
неясности.

Человек отвечает:

- текстом замечания — агент привязывает его к строкам через `gr comment add` и
  подтверждает одной строкой (`записал: nit, transfer.go:57–58, suggestion`);
- вопросом — агент отвечает коротко и остаётся на шаге;
- `n` / «дальше» — агент применяет правила остановки и делает `gr step next`.

В v1 все комментарии идут через чат. Схема комментария в состоянии уже
рассчитана на то, что в v2 их будет писать и вьювер: агент при этом не
меняется.

### 4. Правила остановки

| Уровень     | Что значит          | Что происходит                                                                                                       |
| ----------- | ------------------- | -------------------------------------------------------------------------------------------------------------------- |
| blocker     | меняет подход       | транзитивно зависимые шаги → `stale`; агент спрашивает: «дальше смотрим независимые (N шагов) или публикуем сейчас?» |
| major       | локальная переделка | зависимые шаги помечаются «может измениться», идём дальше                                                            |
| minor / nit | мелочь              | идём дальше; nit с очевидным фиксом становится suggestion                                                            |

Распространение `stale` делает `gr` по графу `depends_on`, а не агент.

### 5. Wrap-up

1. Гейт в `gr status`: все core-шаги и хотспоты — `done` или `skipped` с
   причиной. Без этого агент не переходит к итогу.
2. Агент предлагает вердикт (approve / changes requested / blocked), список
   blocker/major, число nit'ов и покрытие
   (`core 9/9, hotspots 3/3, generated 14 файлов не смотрели`). Человек правит
   в чате.
3. `gr publish --dry-run` показывает, что уйдёт в MR.
4. `gr publish` публикует.

## Вьювер `gr view`

Показывает только текущий шаг и перерисовывается при изменении состояния
(fsnotify).

```
s3/12 logic · POST /transfers — хендлер              ⚑ consistency
───────────────────────────────────────────────────────────────
 api/transfer.go
  40 │  func (h *Handler) Create(ctx context.Context, ...
 +41 │      if err := req.Validate(); err != nil {
 ⚑57 │      h.repo.Reserve(ctx, req.Amount)
 -58 │      return nil
```

- Новая версия кода с полем `+`/`-`/`⚑`, удалённые строки на месте, несколько
  строк контекста; `tab` расширяет контекст.
- Клавиши: `j`/`k`, `]h`/`[h` (hunk'и), `gd` / `gr` / `K` (definition,
  references, hover в скроллируемом попапе), `enter` — провалиться, `ctrl-o` —
  назад, `e` — `$EDITOR` на строке в tmux-popup, `q` — выход.
- Больше ничего: ни дерева файлов, ни табов, ни тем.

LSP:

- сервер по расширению файла: дефолты `gopls`, `basedpyright-langserver`,
  `kotlin-lsp`, переопределяются в `.review.yaml`;
- свой минимальный клиент: JSON-RPC по stdio, `initialize`, `didOpen`,
  `definition`, `references`, `hover`;
- работает по рабочему дереву, поэтому `gr init` требует HEAD == sha MR и
  предлагает `git checkout`. Отдельный worktree — возможное расширение
  (Gradle-импорт в новом worktree медленный);
- сервера нет или он упал после одного перезапуска → вьювер работает без
  навигации и подсказывает, что поставить.

Стек: bubbletea + lipgloss, chroma.

## GitLab

`gr` не содержит своего HTTP-клиента: транспорт — `glab api` (авторизация,
self-hosted, прокси уже решены там). Запросы `gr` собирает сам:

- `position` с `base_sha` / `start_sha` / `head_sha` и маппингом old/new строк;
- draft notes, затем один `bulk_publish` — автору одно уведомление;
- nit с фиксом — блок ` ```suggestion:-0+N `;
- итог ревью — обычная заметка в MR;
- approve — только по явному `--approve`;
- ID опубликованного сохраняются в состоянии, повторный `publish` ничего не
  дублирует;
- если в MR появились новые коммиты, `publish` предупреждает и ставит
  комментарии на просмотренную версию диффа (старые sha в `position`).

Агент пользуется `glab` напрямую только на чтение. Писать в MR — только через
`gr publish`, иначе обходятся гейт и dry-run.

## Ошибки

| Ситуация                          | Поведение                                                        |
| --------------------------------- | ---------------------------------------------------------------- |
| невалидный план                   | `gr plan set` отклоняет и перечисляет проблемы, агент исправляет |
| HEAD ≠ sha MR                     | `gr init` останавливается и предлагает `git checkout`            |
| новые коммиты в MR во время ревью | предупреждение в `gr status` и `gr publish`                      |
| LSP упал                          | один перезапуск, дальше без навигации                            |
| `glab` нет или не авторизован     | сообщение и готовая команда                                      |

## Тестирование

- Go, табличные тесты: детект генеренки, валидация плана, переходы состояний и
  распространение `stale`, сборка `position`.
- GitLab: golden-тесты payload'ов на записанных ответах API.
- Вьювер: несколько snapshot-тестов через `teatest`.
- Скил: прогоны на 4–5 реальных MR (REST-фича, миграция, рефакторинг, багфикс,
  MR с генеренкой). Чек-лист: порядок обхода разумный, пояснения ≤ 5 строк,
  нить не теряется после сжатия контекста, хотспоты найдены.

## Структура репозитория

```
cmd/gr/                  main
internal/
  diff/ classify/        дифф, детект генеренки
  plan/ state/           схема, валидация, переходы
  lsp/ view/             LSP-клиент, TUI
  gitlab/                обёртка над glab api
skills/guided-review/
  SKILL.md               протокол
  references/            ordering.md, hotspots.md, style.md
.claude-plugin/          плагин для Claude Code
AGENTS.md                протокол для Codex
```

Установка: `go install …/cmd/gr@latest` и плагин из marketplace.

## Вне v1

- Комментарии из вьювера (схема готова).
- Переход по шагам из вьювера (`gr wait`).
- GitHub-адаптер.
- Отдельный worktree под ревью.
